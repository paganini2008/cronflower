Distributed cron for the JVM, with a console.

cronflower is a distributed, stateful cron scheduler that forms its own cluster and needs no external database, broker, or coordinator. Drop @Task on a Spring bean and the cluster owns the schedule; declare a @Dag and it runs a whole workflow across your machines.

Get Started GitHub Documentation
cronflower = cronsmith (distributed scheduling) + cronflow (DAG orchestration)

Why cronflower?

@Scheduled and chained cron jobs break down the moment you scale out. Here's what hurts.

Scale out and it fires twice

@Scheduled runs in every JVM, so two instances mean two fires. You end up bolting on Quartz, a database and a lock table.

No retry, timeout, or history

A failed or hung job just fails. There is no record of what ran, no backoff, no misfire policy — you build the dashboard yourself.

Chained cron isn't a workflow

"02:00 charge, 02:15 ship" has no real dependency and no shared data; you can't tell if step two ran because step one succeeded.

Clusters mean heavy infra

Most distributed schedulers need ZooKeeper/etcd, a broker, or an external load balancer just to stand up.

Everything a scheduler needs, nothing to provision

Embedded store, self-forming cluster, self-balancing console.

◈

Self-clustering & HA

Nodes gossip and elect a leader — no ZooKeeper or etcd. Followers fail over; no cron fires twice, none goes missing.

⛁

Stateful & durable

Schedules and history in a store auto-detected from the JDBC URL (H2 → MySQL/PostgreSQL). A restart loses nothing.

⚡

Scales horizontally

A timing wheel drives large volumes; group sharding spreads them and weighted dispatch fans out to executors by capacity.

⌗

Rich @Task model

Cron, year-based YCRON, interval or ISO-8601 — plus retry, timeout, misfire policy and repeat/stop-at, all declarative.

⤳

DAG orchestration

Declare a @Dag with typed channels, branching, joins, subgraphs and dynamic fan-out, driven across the cluster.

▤

Operator console

Tasks, Executors, Cluster, DAG runs, Health and live Settings — one endpoint, UTC-first with a local toggle.

How it works

A console talks to one endpoint; a self-electing scheduler cluster owns the schedule and dispatches due runs to your executors. State lives in an auto-detected store, so a restart or failover loses nothing.

From clone to a live cluster in one command

Nothing to provision — the store is an embedded H2 file and the nodes elect a leader themselves. Open http://localhost:7200 and sign in with admin / admin123.

Browse the repo

# clone and run — scheduler + console + 1 executor
git clone https://github.com/paganini2008/cronflower
cd cronflower/deploy
./run-local.sh -e 1

# scale into a cluster:
./run-local.sh -n 3 -e 2

Examples

Schedule a method, or orchestrate a whole workflow — both are plain Spring beans.

// A distributed task: cron, retry, timeout, YCRON
@Task(cron = "0 0 12 * * ?", name = "rollup",
      maxRetryCount = 2, timeout = 30_000)
public void nightlyRollup() { ... }
// A DAG: fan out, join, decide
@DagNode(entry = true, to = {"credit", "income"})
public Map<String,Object> intake(DagState s) { ... }

@DagNode(trigger = "ALL")
public Map<String,Object> decide(DagState s) { ... }
